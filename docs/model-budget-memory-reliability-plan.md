# 模型预算与记忆整理可靠性计划

日期：2026-11-10。此计划的代码改造已实施，结果与仍存在的运行边界见[交付说明](model-budget-memory-reliability-delivery.md)；本文保留设计与验收目标，不能将目标当作已测结果。

## 目标与边界

用户主动对话不设置应用侧每日调用额度，也不能因后台预算耗尽而停止回复或长时间等待记忆整理。记忆整理允许延后，但不能丢资料、无限重试或把尚未入库的内容报告为成功。

用户于本计划制定后明确要求“用户对话部分不受限”，据此替换原先“每日总上限＋聊天预留”的方案；前台不限额已在代码中实现，部署与验收情况见交付说明。

保留现有 Python、React、PostgreSQL/pgvector 和三层记忆框架，先修调用控制与整理链路，不引入新的消息中间件，不清空业务数据，不重写人格与对话风格。移动端及陪伴界面规划另行保留。

## 已核实的现状

- 200 次是常驻服务自己设定的每日模型请求上限，不是供应商规定的账户额度。状态、回复、后台整理等共用它；一次聊天可能产生多次请求。
- 本次故障当天达到 200 次，其中记忆编码成功 11 次、失败调用 136 次。日志确认模型请求反复超时；上下文较大、非流式完整输出和旧 20 秒配置是可能的促成因素，尚不能排除网关与网络响应问题。
- 已上线止损：后台最多占基础模型预算的 75%；整理默认最多 60 秒、单次尝试、持久指数退避；原始资料与任务保留；前端显示部分具体错误。仅 2026-11-10 经授权临时提高至 300，次日恢复基础 200。
- 当前仍有不足：预算分组固定、页面缺少调用来源明细；`one_chat` 多数异常最终变成空结果；编码模型调用发生在世界操作锁内；向量写入重试可能重新计算已经成功的向量。
- 简短模型连通性验证通过，不代表积压批次已成功完成。完整恢复必须另行验收。

## 一、预算管理：聊天优先，后台有界

### 1. 明确计量与配置含义

界面统一使用“应用调用预算”，与供应商余额、限流分开展示。区分对话回复、对话状态与工具续接、记忆编码、主动发言、空闲演化、向量、语音。

取消用户主动对话链路的应用侧每日次数/Token 配额。豁免范围包括回复生成、本轮必要的状态准备、工具调用与结果续接、召回所需查询向量，以及该回复的自动语音和用户手动重播所需生成。正常保留用量统计，不因统计达到 200 或 300 而拦截。

后台使用独立的每日预算、记忆子预算、请求速率和并发限制，不再以用户调用量扣减。迁移时可沿用当前后台 150 次模型调用作为初始上限，后续独立配置；后台向量和语音也按后台来源计量。旧总上限与当日临时覆盖不再作用于用户链路，也不能把追加给用户的额度自动变成后台额度。

调用归属必须由可信的任务上下文传递，包含用户轮次 ID 或后台任务 ID，不能只凭 `state_update` 等用途名称判断；后台同样可能更新状态。用户说“请记住”后本轮回复与原文持久保存不受额度拦截，后续长期提炼仍属于有界的后台工作。前台点击重试后台任务也不改变其归属。

仍保留有限自动重试、同消息去重、必要的排队与并发控制，防止一次故障造成无限外部调用；这些不构成用户的每日聊天额度。供应商的余额、限流和服务故障独立存在，应按真实原因提示。

每天按现实 Asia/Shanghai 日界线统一统计；模型逻辑时间、时间加速和读档均不能恢复调用预算。日期边界显式计算，避免依赖某个数据库连接的会话时区。

每次真实外部请求关联逻辑任务 ID、尝试 ID、用途、模型、耗时、结果、已返回 Token 和安全错误码。超时费用未知时标记“用量未知”，不能按免费处理；被应用预算挡住、尚未发送的请求单独记录为拦截，不算已发出的模型调用。应用统计不冒充供应商账单。

### 2. 优先级与退让

优先级为：当前用户对话所需调用 > 明确要求记住的任务 > 普通记忆整理 > 主动发言与空闲演化。心跳保留，但一次心跳不必触发模型请求：先由程序判断有无变化、未处理资料、合适时机和可用预算。

后台预算耗尽只暂停对应后台工作，保留待办与下一次允许时间；用户聊天继续，不展示“今日应用额度耗尽”。供应商或网络导致回复失败时，消息保持已保存、回复未完成；提供沿用同一消息 ID 的重试入口，避免重发出重复聊天。

用户轮次所需状态、检索与工具步骤跟随前台来源，不会在回复获准后又被后台额度挡住。用户请求之间不设每日总量限制，但单个轮次的工具轮数、输出规模和失败重试仍有边界，不能为了追求无限自动调用形成死循环，也不能为了省调用伪造状态或跳过必要校验。

### 3. 页面反馈

设置中明确展示“用户对话：应用不设每日额度”，同时显示累计用量；后台单独展示上限、各用途成功/失败/未知次数、Token 与下一次重置时间。旧临时总上限若已不参与前台判定，不再显示为用户可用额度。后台接近上限或暂停在状态区提示，避免每次聊天弹出同一错误。

修改上限需由用户明确操作并保存；应用不能自动加额度。若将来展示金额，必须提供可配置模型价格、更新时间和估算标识；本轮不实现未经核实的精确费用承诺。

## 二、记忆整理：可恢复的小任务

### 1. 先让错误可诊断

LLM 层提供带类型的调用结果或异常，保留现有调用方兼容适配，避免全局修改后其他状态流程失效。至少区分：应用预算等待、供应商限流、请求超时、连接失败、认证/配置错误、上下文超限、结果格式/引用校验失败、向量失败、数据库失败。

每批记录输入规模、阶段耗时、尝试次数、安全错误码及下次动作。日志只保存定位元数据，不输出密钥、供应商原始异常正文或完整私人聊天。先用这些信息判断大批次、输出耗时、网络、向量或数据库哪一环失败，不能仅凭简短调用成功就宣布根因消失。

### 2. 按消息边界分批并限制工作量

从未处理来源增量取材，按模型适配器的 Token 估算与保守字符兜底控制总上下文，给提示词和输出预留空间。批次从较小规模起步，经实际耗时校准，遇上下文超限或重复慢请求再按来源边界拆分；不能只延长超时。

单条超长消息可拆为带原消息 ID、片段序号及位置的子来源，原文完整保留。新消息进入后续批次，不让失败批次无限膨胀。批次 ID、来源版本和编码结果持久化，重试同一批沿用标识。

提炼偏好、事项、约定时继续校验原文引用、说话人、时间来源和置信度；明确的“请记住”可以先进入有来源的工作记忆，长期整理完成前仍标记为待整理，不把本地保留冒充向量入库成功。模型判断“没有值得长期保存的内容”也要记录为成功处理且无新增，区别于失败或丢资料。

### 3. 分阶段保存进度

任务阶段为：待编码 → 编码结果已校验并落盘 → 待向量 → 待数据库提交 → 已收到提交回执 → 已安全确认来源处理完成。

每阶段先持久化，再进入下一阶段。正文/洞察向量成功后保存可复用结果或缓存引用，缓存键包含内容摘要、模型与维度；后续数据库重试不重新请求向量。修改来源或更换模型时不能误用旧向量。

保留稳定 memory_id 与数据库唯一约束，确保重放不会重复入库；外部模型请求超时后是否已执行无法保证，因此不承诺 API 恰好调用一次。

仅在整批提交确认后消费相应日志前缀。拆分后的子批次按来源顺序确认，前方存在缺口时不越过；旧日志和追加的新记录不能被误删。兼容现有待办、失败向量文件与旧存档，不强制重新编码全部历史。

### 4. 分类重试与熔断

| 故障 | 处理 |
|---|---|
| 应用预算不足 | 等预算恢复，不当作一次外部失败，不反复探测模型 |
| 供应商限流 | 优先遵守可用的 Retry-After，再退避 |
| 超时、连接错误、可恢复服务错误 | 1、2、4 分钟起逐步退避并加入少量随机间隔，设置每任务自动尝试上限 |
| 同一模型/服务连续失败 | 暂停受影响的后台通道，到期只放行一个探测任务，避免其他批次一起重试 |
| 认证、模型名或配置无效 | 暂停并提示修配置，配置变化后再恢复 |
| 上下文超限 | 先缩小/拆分批次，不原样重复发送 |
| JSON 或引用不合法 | 最多一次有界修正；仍失败则保留批次并等待处理，不接受无来源记忆 |
| 向量或数据库失败 | 从失败阶段继续，不重复已成功的编码与向量请求 |

建议初始每批最多连续自动尝试 3 次；超限进入明确的“需要处理”状态，保留资料，配置修复或手动重试后才重开尝试。失败次数、熔断时间与预算等待需要重启后仍生效。用户对话不被后台熔断直接关闭，但仍遵守自身失败与速率保护。

## 三、调度：不让整理阻塞对话

将编码移出世界操作锁：短时间持锁领取任务并拍下来源快照，释放锁后请求模型，回来提交时再校验世界/读档代次、任务版本与来源前缀。复用现有工作记忆待办，增加单工作者领取/租约与重复提交保护，不要求新增队列服务。

已有网络请求不能保证瞬间取消；必须设置可执行的整体截止时间与有限并发，用户输入到达后停止启动新的普通后台批次，当前编码不再占对话串行锁。不能把一次慢调用变成无限等待。

存读档仍等待或安全取消当前工作，再切换世界代次；旧代次返回结果不能写入新档。正常新增聊天不应一律使快照失效，只校验本任务所覆盖的来源。调用消费属于现实使用记录，读档后保留，不随世界回滚。

## 四、恢复与界面

记忆状态显示：等待整理、正在编码、生成向量、入库中、完成无新增、已完成、预算暂停、退避等待、需要处理。展示待办数量、最老待办时间、最近成功时间、错误类别与下次尝试时间，避免只有一个笼统的“失败”。

提供“重试这一批”“暂停后台整理”“查看安全诊断摘要”。重试继续原任务，不重新制造同一批来源；暂停与重试不能绕过预算、认证故障或存读档保护。批量重整全部历史不作为默认按钮。

积压恢复从一小批开始，确认编码、向量、数据库回执及召回都成功后才逐步处理剩余批次。按后台预算推进，不以追赶积压为由占满对话所需并发或自行提高后台付费上限。

## 五、实施顺序与交付

1. **P0：前台不限额与后台调用控制。**先贯通可信的调用来源，取消用户链路的应用侧每日配额，再补充结构化错误、按用途用量、后台独立配置、统一日期边界、预算等待和持久熔断。保留后台止损与有限重试规则。交付：用户不限额、后台仍受控的验收记录，用量明细、清晰故障分类及回归测试。
2. **P1：记忆任务可靠性。**实现小批次、阶段检查点、有限重试、向量复用及旧待办兼容。交付：断点恢复、去重及来源确认测试。
3. **P1：解除对话阻塞。**任务快照、锁外模型请求、提交校验、存读档代次隔离。交付：慢模型下聊天与读档并发验收。
4. **P2：恢复交互与实际验收。**完成状态页、同消息重试和诊断；在隔离库验证真实整理与召回，再备份当前业务状态，受控恢复积压。交付：前后待办对比、失败原因报告、使用和回退说明。

涉及文件主要为 `service/store.py`、`core/service_policy.py`、`brain/llm_client.py`、`memory/memory_process.py`、`memory/working_memory.py`、`memory/episodic_memory.py`、事件/存档协调模块以及前端服务状态和记忆状态组件。

## 六、验收标准

- 所有自动测试使用模拟模型、临时配置和独立测试库，不能清空业务数据库或调用真实付费 API。
- 模拟大量后台失败后，后台在规定次数内停止；前台超过原 200/300 次仍能继续，状态、工具续接、查询向量与回复语音不会被后台额度间接拦截，全部调用保留统计。
- 覆盖上海跨日、旧临时上限到期、并发预算预留、模拟时钟加速、读档、后台预算拦截不发请求；前台量不扣减后台预算，后台不能伪装成用户调用，单次故障不会无限重试。
- 覆盖超时、限流、错误密码、无效模型、上下文超限、非法 JSON/来源、向量失败、数据库断连及每个检查点崩溃；只从必要阶段继续。
- 同一批任务反复投递/重启后无重复长期记忆，已成功向量不因纯数据库重试重新调用；确认前原始资料保持可恢复。
- 慢编码测试中用户对话可先完成；读档后旧任务结果被拒绝，新档与当前调用统计均正确。
- 独立环境中以少量真实模型调用验证“有来源的输入 → 编码 → 向量 → 入库 → 工具召回 → 模型消费结果”，记录实际耗时和调用数量。短请求连通性不是替代验收。
- 本机运行观察覆盖空闲、连续聊天、积压恢复三种情形，确认无失败风暴、无待办静默卡死、无聊天重复或数据丢失。报告实际测量值，不预先宣称已满足时延或费用指标。
- 上线前保留配置、镜像与业务恢复点；回退停止新调度后恢复旧镜像与配置，保留数据库卷和全部待办。若任务格式升级，提供可读的兼容适配及开关，不能回退后静默遗弃新任务。
